# Automation Tab — Data Models & API Endpoints

This document describes the server-side API contracts required to replace the
client-side mock data in `frontend/react/src/shell/tabs/AutomationTab.tsx`
with live endpoints. The Automation tab is the operations surface at
`#/automation` covering routing rules, SLA policies, escalation workflows,
macros & templates, and the automation impact summary (KPI strip,
metric cards, 14-day coverage chart).

Each section below follows the same shape:

- **Source in client** — the local constant, interface, or component
  that consumes the data.
- **Endpoint** — the suggested HTTP method, path, query parameters,
  and payload.
- **Response shape** — the JSON the server must return, with field
  types and notes about how the client transforms it.
- **Notes** — gotchas, contract nuances, the `ChipTone` / `TabKey` /
  etc. enums, and any client-side derivation the server should be
  aware of (e.g. team/priority/usage filters are applied on the
  client; the server only returns the master list).

The page is filter-driven: a single page-level reducer holds
`environment` / `team` / `range` / `activeTab`, and a per-section
`useState` set holds the `routing` (team, priority), `sla` (queue,
priority), `macro` (team, usage), and `impact` (range) sub-filters.
The list below groups endpoints by the **view** they serve, then
calls out the filter contract that all of them share.

### Per-section sub-filter state ownership

The page-level reducer (§0) and the per-section `useState` set
are separate state slices that share some value types but
serve different dropdowns:

| Filter        | Owner              | Value type     | Wired to API? | Notes                                                       |
| ------------- | ------------------ | -------------- | ------------- | ----------------------------------------------------------- |
| `environment` | Page reducer       | `EnvironmentKey` | no          | Top toolbar dropdown. Reserved for future global filter.    |
| `team` (page) | Page reducer       | `TeamKey`      | no            | Top toolbar dropdown. Reserved for future global filter.    |
| `range`       | Page reducer       | `RangeKey`     | yes (§5.1)    | Top toolbar dropdown. Drives the KPI strip range.           |
| `activeTab`   | Page reducer       | `TabKey`       | n/a           | Tab selection only.                                         |
| `teamFilter`  | Routing section    | `TeamKey`      | **yes (§1)**  | Only client-side filter that actually narrows the rows.    |
| `priorityFilter` | Routing section | `PriorityKey`  | no            | Captured in state, fires a toast, but does not filter rows. |
| `slaQueue`    | SLA section        | `TeamKey`      | no            | Captured in state; passed to `onSlaSeedDraft` only.         |
| `slaPriority` | SLA section        | `PriorityKey`  | no            | Captured in state; passed to `onSlaSeedDraft` only.         |
| `macroTeam`   | Macros section     | `TeamKey`      | no            | Captured in state, fires a toast, but does not filter rows. |
| `macroUsage`  | Macros section     | `MacroUsageKey` | no           | Captured in state, fires a toast, but does not sort macros. |
| `impactRange` | Impact sub-section | `ImpactRange`  | no (UI-only)  | Drives the 7d/30d/90d segmented button styling + label.     |

`MacroUsageKey` is the union of `MACRO_USAGE_OPTIONS`:
`'most-used' | 'recent' | 'alphabetical'`.

## 0. Shared enums & filter contract

These enums are used by every endpoint below. They are re-declared
in `AutomationTab.tsx`. The server should treat them as the canonical
set of values; the client hardcodes display labels and colors.

```ts
// Chip tone — the client maps this to a CSS class
// (e-success / e-warning / e-danger / e-info / e-secondary).
// Unknown values fall through to 'e-secondary' (neutral).
type ChipTone = 'success' | 'warning' | 'error' | 'info' | 'neutral';

// Toast severity — drives the toast surface's color band.
type ToastSeverity = 'Success' | 'Info' | 'Warning' | 'Error';

// Top-level tab key — one per section tab in the Automation page.
// `count` is the number of items in that section (rendered in
// the tab label as "Routing rules (12)"). The literal 'all' is
// not a tab; tabs are specific to each section.
type TabKey = 'routing' | 'sla' | 'escalation' | 'macros-impact';

// Page-level environment filter — drives the top toolbar dropdown.
type EnvironmentKey = 'all' | 'prod' | 'staging' | 'dev';

// Page-level team filter — drives the top toolbar dropdown and the
// `TEAM_OPTIONS` reuse in the per-section sub-filters.
type TeamKey = 'all' | 'platform' | 'billing' | 'account' | 'general';

// Page-level range filter — drives the top toolbar dropdown. Applies
// to the KPI summary strip and the routing grid counts.
type RangeKey = '7d' | '30d' | '90d';

// Priority filter — multi-select, used in the routing sub-filter
// and the SLA new-policy form. Empty array means "no priorities".
type PriorityKey = 'p1' | 'p2' | 'p3' | 'p4';

// Impact range — segmented control on the Macros & Impact section.
// Independent of the page-level `RangeKey`.
type ImpactRange = '7d' | '30d' | '90d';

// Routing rule status — drives the Status column chip in the
// routing rules grid.
type RuleStatus = 'active' | 'paused';

// SLA strictness — drives the pill chip on each SLA policy row.
type SlaStrictness = 'Strictest' | 'Tight' | 'Standard' | 'Relaxed';

// Builder step kind — drives the colored letter icon (T / C / A)
// and the connector color in the escalation workflow builder.
type BuilderKind = 'trigger' | 'condition' | 'action';

// Macro card status — drives the small dot + label in the macro
// card meta row.
type MacroStatus = 'active' | 'draft';

// KPI card severity — drives the sparkline fill colour and the
// card's outer CSS class (`kpi-tile--{tone}`). The mapping is
// hardcoded client-side via `KPI_SEVERITY_COLOR` (see §5.1).
// The four seed values are 'normal' / 'info' / 'warning' /
// 'critical'; the client maps 'normal' → success, 'critical' →
// danger, and the other two pass through unchanged.
type KpiSeverity = 'normal' | 'info' | 'warning' | 'critical';
```

### 0.1 Per-endpoint filter contract

The read endpoints (§1–§7) accept a *subset* of the page-level
filters (`environment`, `team`, `range`) and *per-section*
sub-filters where the client actually filters the data. Re-issuing
a request with the same filter set is a no-op for the client (the
reducer skips unchanged dispatches) but should be safe for the
server to handle idempotently.

| Endpoint                                  | `environment` | `team`     | `range`  | Per-section filters actually applied     |
| ----------------------------------------- | ------------- | ---------- | -------- | ---------------------------------------- |
| `GET /api/automation/routing-rules`       | reserved      | **yes** (rule-id mapping, see §1) | reserved | `routing.team` filters rows. `routing.priority` is captured client-side but does **not** filter rows. |
| `GET /api/automation/sla-policies`        | reserved      | reserved   | reserved | `sla.queue` / `sla.priority` are captured but do **not** filter rows. |
| `GET /api/automation/escalation-workflows/{id}` | reserved | reserved   | reserved | (none — single workflow per id)          |
| `GET /api/automation/macros`              | reserved      | reserved   | reserved | `macro.team` / `macro.usage` are captured but do **not** filter or sort the list. |
| `GET /api/automation/impact/kpis`         | reserved      | reserved   | **yes**  | (single `range` query parameter)         |
| `GET /api/automation/impact/metrics`      | reserved      | reserved   | **yes**  | (`ImpactRange` value, default `30d`)     |
| `GET /api/automation/impact/coverage`     | reserved      | reserved   | **yes**  | (`ImpactRange` value, default `30d`)     |

The reserved columns mean the server should still accept (and
ignore) the parameter, so the client can pass them through
without re-shaping the URL.

| Param         | Type            | Required | Default       | Notes                                              |
| ------------- | --------------- | -------- | ------------- | -------------------------------------------------- |
| `environment` | `EnvironmentKey`| no       | `all`         | One of `all`, `prod`, `staging`, `dev`.            |
| `team`        | `TeamKey`       | no       | `all`         | One of `all`, `platform`, `billing`, `account`, `general`. |
| `range`       | `RangeKey`      | no       | `7d`          | One of `7d`, `30d`, `90d`.                         |

Example: `GET /api/automation/routing-rules?environment=prod&team=billing&range=7d`
(returns only rules with `id` matching the `billing` team
substring — see §1 for the rule-id mapping).

## 1. Routing rules

### Source in client
`AutomationTab.tsx` — `RoutingRule` interface and the
`ROUTING_RULE_ROWS` / `SEED_RULES` constants (10 records). Consumed
by `RoutingRulesGrid` (Syncfusion `GridComponent`) and the per-row
context menu. The grid renders **6 columns**: Rule (template),
Owner (field), Target (field), Matched (7d) (template), Last run
(field), Status (template). There is no per-row `SwitchComponent`
column — `SwitchComponent` is not imported; the on/off toggle from
the earlier draft was replaced with a right-click context menu
(Edit / View history / Clone).

### Endpoint

`GET /api/automation/routing-rules`

#### Query parameters

Standard filter set (see §0.1).

#### Response

```ts
{
  rules: Array<{
    id: string;                  // unique id, e.g. "rule-billing"
    title: string;               // h1 in the Rule cell, e.g. "Billing → Billing Tier 2"
    sub: string;                 // monospaced predicate, e.g. "queue=billing AND plan=enterprise"
    owner: string;               // free-form owner label, e.g. "Daniel K." or "System"
    target: string;              // destination label, e.g. "Billing · Tier 2"
    matched: number;             // match count in the active range, e.g. 412
    matchedDelta: string;        // signed delta vs prior period, e.g. "+38", "−12", "0"
    lastRun: string;             // human label, e.g. "4m ago", "1h ago"
    status: RuleStatus;          // drives the Status column chip
    enabled: boolean;            // persisted toggle (no per-row Switch in the current UI; reserved for the future PATCH endpoint)
  }>;
  totalCount: number;           // total rules in the filtered set (for the section header)
  activeCount: number;          // subset with `status === 'active'`
}
```

#### Notes

- `matchedDelta` is a string (not a number) because the UI
  renders the leading sign verbatim and the zero case is shown
  as `"0"`. The `−` (U+2212) minus sign and the ASCII `-` both
  mean "down"; the client accepts either. The per-cell colour
  is computed client-side:
  - `matchedDelta === '0'` → `text-text-subtle`
  - starts with `−` or `-` → `text-danger`
  - everything else → `text-success`
- `lastRun` is a pre-formatted human label; the server should
  compute it from the `lastRunAt` timestamp using the
  active `range` and the user's locale.
- The grid's per-row context menu items (Edit / View history /
  Clone) are client-only — they fire a toast and never call
  the server in the showcase. The server still needs to
  reserve `id` for future use as a route parameter. The
  context menu items are wired through `contextMenuItems` on
  the `GridComponent` (three entries with `id`s
  `rule-edit` / `rule-history` / `rule-clone`).
- The per-row `Switch` column that existed in an earlier
  draft of the file is gone; `enabled` is still part of the
  contract so the server can record the toggle when the
  future `PATCH /api/automation/routing-rules/{id}` lands.
- The section header shows `{N} active · last edited 14m ago`
  where `N` is `rules.filter(r => r.enabled).length` — i.e. it
  counts the `enabled` boolean, not the `status` enum. The
  "last edited 14m ago" copy is hardcoded in the showcase and
  is not part of the API contract.

#### Team filter — rule-id mapping

The per-section **team** dropdown on the routing tab (a
`TeamKey`) is the only client-side filter that actually
narrows the visible rows. Because the seed data does not
carry a `team` field on each rule, the client infers team
membership from the rule id. The same mapping must be
implemented on the server so the `team` query parameter on
`GET /api/automation/routing-rules` returns the same set:

| `team`     | Rule ids matched (substring)                          |
| ---------- | ----------------------------------------------------- |
| `all`      | (no filter — return every rule)                      |
| `platform` | `rule-enterprise-outage`, `rule-after-hours`         |
| `billing`  | `rule-billing`, `rule-chargeback`                    |
| `account`  | `rule-vip`, `rule-vip-asia`                          |
| `general`  | `rule-latam`, `rule-overflow`                        |

The `rule-spam` and `rule-low-csat` ids are intentionally not
matched by any team. When the server model gains an explicit
`team` field on `RoutingRule`, the substring rule should be
deprecated in favour of an exact match.

## 2. SLA policies

### Source in client
`AutomationTab.tsx` — `SlaPolicy` interface and the `SLA_POLICIES`
constant (4 records). Consumed by `SlaPoliciesSection` (Syncfusion
`ListViewComponent`) and the right-hand "new policy" form (queue +
priority + "New policy" CTA).

### Endpoint

`GET /api/automation/sla-policies`

#### Query parameters

Standard filter set (see §0.1).

#### Response

```ts
{
  policies: Array<{
    id: string;                  // unique id, e.g. "enterprise-p1"
    title: string;               // h1, e.g. "Enterprise · P1"
    sub: string;                 // scope line, e.g. "First response · Resolution · Next response"
    strictness: SlaStrictness;   // drives the pill chip on the right
    strictnessTone: ChipTone;    // chip color (e.g. 'error' for Strictest, 'neutral' for Relaxed)
    pills: Array<{               // SLA thresholds rendered as monospaced pills below the title
      label: string;             // e.g. "First response", "Next response", "Resolution"
      value: string;             // e.g. "15m", "1h", "4h", "24h", "5d"
    }>;
  }>;
  totalCount: number;           // total policies in the filtered set
}
```

#### Notes

- `strictnessTone` is denormalized so the client can color the
  pill without re-deriving it. Allowed values: `'error'` for
  `Strictest`, `'warning'` for `Tight`, `'neutral'` for
  `Standard` / `Relaxed`.
- The "new policy" form on the right does not POST in the
  showcase (the "New policy" button fires a toast). The
  server should reserve `POST /api/automation/sla-policies`
  for the future — payload shape will mirror the response
  plus an optional `description` string.
- The `pills` array is variable-length per policy (1–3 items).
  The minimum is "Resolution" only; the maximum is "First
  response" + "Next response" + "Resolution".
- The list section header has a hardcoded sub-line
  "By priority & customer plan". The "new policy" form on
  the right uses two `TeamKey` / `PriorityKey` dropdowns
  (`slaQueue` + `slaPriority`). **The current client only
  uses these two values to seed the toast on
  `onSlaSeedDraft(queue, priority)` — they are not used to
  filter the `SLA_POLICIES` master list.** When the server
  grows the ability to scope SLA policies by queue and
  priority, the same `slaQueue` / `slaPriority` query
  parameters should be accepted on the read endpoint and
  the dropdowns should refetch.

## 3. Escalation workflows

### Source in client
`AutomationTab.tsx` — `BuilderStep` interface, the
`WORKFLOW_STEPS` constant (5 records) for the current workflow,
and the `WORKFLOW_PALETTE` constant (5 records) for the
"Available blocks" sidebar. Consumed by `EscalationSection`.

### Endpoint

`GET /api/automation/escalation-workflows/{id}`

#### Path parameters

| Param | Type   | Required | Notes                                              |
| ----- | ------ | -------- | -------------------------------------------------- |
| `id`  | string | yes      | The workflow id, e.g. `wf-platform-spike`.         |

The client currently only renders one workflow. The id is
passed as a fixed `"current"` for the showcase; the server
may reserve the route for future per-workflow navigation.

#### Query parameters

Standard filter set (see §0.1).

#### Response

```ts
{
  workflow: {
    id: string;                  // workflow id, e.g. "wf-platform-spike"
    title: string;               // header title, e.g. `Escalation workflow · "Auth > 5 in 10m"`
    subtitle: string;            // header sub-line, e.g. "Routed Tier 3 · auto-page on-call when volume exceeds threshold"
    steps: Array<{
      id: string;                // step id, e.g. "step-trigger"
      kind: BuilderKind;         // 'trigger' | 'condition' | 'action'
      title: string;             // step name, e.g. "Trigger · Ticket created"
      expr: string;              // predicate / DSL expression, e.g. `channel = "chat" OR "email" AND queue = "platform"`
    }>;
    palette: Array<{             // "Available blocks" sidebar items
      id: string;                // e.g. "sla-threshold"
      label: string;             // e.g. "Trigger · SLA threshold"
    }>;
  };
}
```

#### Notes

- `kind` drives the colored letter icon (T / C / A) and the
  soft-tinted background (`bg-info-soft`, `bg-warning-soft`,
  `bg-success-soft`). The three values are stable.
- `expr` is shown verbatim in monospaced text; the server is
  the source of truth for the expression DSL.
- The `palette` list is workflow-agnostic (same 5 items in
  the showcase regardless of the active workflow). The server
  may return a per-workflow palette in the future by
  filtering on the active `team` filter.

## 4. Macros & templates

### Source in client
`AutomationTab.tsx` — `MacroCard` interface and the `MACROS`
constant (6 records). Consumed by `MacrosImpactSection` (a
grid of `MacroCardItem` instances).

### Endpoint

`GET /api/automation/macros`

#### Query parameters

Standard filter set (see §0.1). The `macro.team` /
`macro.usage` sub-filters are **not** applied in the current
showcase client (they only fire a toast on change); the
server returns the full master list. See §0.0 for the
ownership table and §0.1 for the per-endpoint filter
contract.

#### Response

```ts
{
  macros: Array<{
    id: string;                  // unique id, e.g. "macro-reset-password"
    name: string;                // display name, e.g. "Reset password"
    shortcut: string;            // keyboard shortcut, e.g. "/rp"
    body: string;                // full template body with `{{placeholder}}` tokens
    usage: string;               // pre-formatted human label, e.g. "Used 412× · 7d"
    status: MacroStatus;         // 'active' | 'draft'
  }>;
  totalCount: number;           // total macros in the filtered set
}
```

#### Notes

- `body` preserves whitespace (newlines, indentation). The
  client renders it inside a `<pre>`-like block with
  `whitespace-pre-wrap`. The server should return the raw
  template text — no escaping or wrapping.
- `usage` is a pre-formatted human label; the server
  computes it from the count + active range. Format is
  `Used {count}× · {range}` (e.g. "Used 412× · 7d").
- The "Use" and "Duplicate" buttons on each card fire a
  toast and never call the server in the showcase. The
  server should reserve `POST /api/automation/macros` for
  future "create from template" and `PUT /api/automation/macros/{id}/use`
  for "agent used this macro" tracking.
- The section header has a hardcoded sub-line
  "Reusable replies and shortcuts · 34 macros · 8 templates".
  The "34 macros" / "8 templates" counts are **not** the
  same as `MACROS.length` (which is 6 in the seed); they
  are a static page-level summary the server may keep or
  replace with an `applicationConfig` call in the future.
- The per-section **team** and **usage** dropdowns
  (`macroTeam` from `TeamKey` and `macroUsage` from
  `MACRO_USAGE_OPTIONS`) are wired through state and fire
  toasts on change, but **the current client does not
  filter or sort `MACROS` by either value.** When the
  server supports these dimensions, the read endpoint
  should accept `team` and `sort` query parameters (and the
  client will refetch instead of firing a toast).

## 5. Automation impact

### Source in client
`AutomationTab.tsx` — three separate datasets:

1. **KPI summary strip** (4 cards) — `KpiSummary` interface and
   the `KPI_SUMMARIES` constant. Each card has a sparkline.
2. **Impact metric cards** (3 cards) — `ImpactMetric` interface
   and the `IMPACT_METRICS` constant. Each has a progress bar.
3. **14-day coverage chart** — `COVERAGE_X_LABELS`,
   `COVERAGE_AUTO_ROUTED`, `COVERAGE_AUTO_RESOLVED`,
   `COVERAGE_SLA` constants. Three line series.

The KPI strip is filter-driven by the page-level `RangeKey`
(7d / 30d / 90d). The metric cards and the coverage chart
are filter-driven by the per-section `ImpactRange` segmented
control.

### Endpoints

#### 5.1 KPI summary strip

`GET /api/automation/impact/kpis`

##### Query parameters

| Param      | Type        | Required | Default |
| ---------- | ----------- | -------- | ------- |
| `range`    | `RangeKey`  | no       | `7d`    |

##### Response

```ts
{
  cards: Array<{
    id: string;                  // e.g. "kpi-active-rules"
    label: string;               // e.g. "Active rules"
    value: string;               // pre-formatted, e.g. "26", "78%", "42h 18m"
    chip: {
      label: string;             // e.g. "Healthy", "Of 2,184", "On target"
      tone: ChipTone;            // e.g. "success", "neutral", "info"
    };
    breakdown: Array<{           // chip pills rendered under the value (e-card-actions row)
      count: number;             // integer; 0 hides the leading number badge
      label: string;             // e.g. "routing", "tickets", "+1.8 pts vs last week"
      tone: ChipTone;            // drives the soft background + foreground color
    }>;
    spark: Array<[number, number]>;  // [x, y] tuples; the original x is DISCARDED
    severity: KpiSeverity;       // drives the sparkline fill color via the table below
  }>;
}
```

##### Notes

- The four cards in the showcase are `kpi-active-rules`,
  `kpi-auto-routed`, `kpi-sla-compliance`, `kpi-time-saved`.
  The client hardcodes the layout; the server may return
  any subset (the client renders whatever it gets).
- `value` is pre-formatted; the server picks the right unit
  (`%`, `h m`, integer count, etc.). The client never
  reformats.
- `breakdown` replaces the earlier `sub` string. Each
  `breakdown` entry renders as a soft-tinted pill below the
  value (in the `e-card-actions` row). The `count` is shown
  only when `> 0`; the `label` is always shown. The
  foreground / background colour mapping is hardcoded
  client-side:
  - `tone: 'success'` → bg `var(--color-success-soft, #dcfce7)`, fg `var(--color-success)`
  - `tone: 'info'`    → bg `var(--color-info-soft, #dbeafe)`,    fg `var(--color-info)`
  - `tone: 'warning'` → bg `var(--color-warning-soft, #fef3c7)`, fg `var(--color-warning)`
  - `tone: 'error'`   → bg `var(--color-danger-soft, #fee2e2)`,  fg `var(--color-danger)`
  - `tone: 'neutral'` → default secondary pill styling
- `spark` is a list of `[x, y]` tuples. The client
  transforms the data with `.map(([, y], i) => ({ x: i, y }))`
  before passing it to the Syncfusion `SparklineComponent`,
  so **the original x value is discarded and the array
  index is used as the new x.** The server may return any
  monotonically increasing x values; only the y values are
  rendered.
- `severity` is a `KpiSeverity` enum (see §0). The client
  maps it to a CSS color token via
  `KPI_SEVERITY_COLOR[severity]` and passes that as the
  sparkline `fill`:

  | `severity`  | CSS color token                  | Card CSS class                |
  | ----------- | -------------------------------- | ----------------------------- |
  | `normal`    | `var(--color-success)`           | `kpi-tile--success`           |
  | `info`      | `var(--color-info)`              | `kpi-tile--info`              |
  | `warning`   | `var(--color-warning)`           | `kpi-tile--warning`           |
  | `critical`  | `var(--color-danger)`            | `kpi-tile--danger`            |

- The KPI strip is shared by the page-level top section
  (alongside the page header) AND by the Routing rules
  section's `KpiSummaryStrip`. The same endpoint is the
  source of truth for both placements; the `id` values
  are stable.

##### Hardcoded banner text

The Routing rules section renders a green
`AutomationStatusBanner` above the KPI strip with the
text "All systems normal · 26 rules active, 2 paused,
0 failing" and a sub-line "Next scheduled dry-run in
38 minutes · Drift check passed at 12:30 PM". These
strings are hardcoded in the showcase; the server may
expose them as part of a future `automationStatus`
endpoint or include them in the §1 routing-rules
response under a new `status` object.

#### 5.2 Impact metric cards

`GET /api/automation/impact/metrics`

##### Query parameters

| Param      | Type         | Required | Default |
| ---------- | ------------ | -------- | ------- |
| `range`    | `ImpactRange`| no       | `30d`   |

##### Response

```ts
{
  cards: Array<{
    id: string;                  // e.g. "deflection"
    label: string;               // e.g. "Deflection rate"
    value: string;               // pre-formatted, e.g. "22.6%"
    chip: {
      label: string;             // e.g. "+4.2 pts", "−18%"
      tone: ChipTone;            // 'success' | 'info'
    };
    pct: number;                 // 0-100, drives the progress bar fill
    barTone: 'success' | 'info' | 'primary';   // drives the progress bar color
    helper: string;              // e.g. "Resolved without an agent", "Best in 8 weeks"
  }>;
}
```

##### Notes

- `pct` is a number 0–100, not a string. The progress bar's
  track color is always `var(--color-surface-2)` (set in
  CSS) and the fill color comes from `barTone` (mapped to
  `var(--color-success)` / `var(--color-info)` /
  `var(--color-primary)` in the client).
- `chip.label` is a signed delta string. The `−` (U+2212)
  minus sign and the ASCII `-` are both accepted.
- The current showcase client **does not refetch this
  endpoint when the user changes the `impactRange`
  segmented control** — it only updates the label copy
  ("Last 7 days · …" etc.) and the button styling. The
  contract is in place for the server to implement; the
  §5.1 KPI strip is the only one of the three §5 endpoints
  that the showcase actually refetches (via the page-level
  `RangeKey` dropdown).

#### 5.3 14-day coverage chart

`GET /api/automation/impact/coverage`

##### Query parameters

| Param      | Type         | Required | Default |
| ---------- | ------------ | -------- | ------- |
| `range`    | `ImpactRange`| no       | `30d`   |

##### Response

```ts
{
  xLabels: string[];             // 14 day labels, e.g. ["D-14", "D-13", ..., "today"]
  series: {
    autoRouted: number[];        // 14 data points, y values 0-100 (percent)
    autoResolved: number[];     // 14 data points
    sla: number[];               // 14 data points
  };
}
```

##### Notes

- The three series must be returned in the same order
  (oldest → newest) and have the same length as `xLabels`.
  Length mismatches render a Syncfusion warning; the server
  should reject any request that cannot satisfy the
  invariant.
- The chart's primary Y axis is hardcoded to `0–100%` with
  a 25-unit interval. Series values outside that range
  clip at the axis; the server should normalize to 0–100
  before responding.
- The series labels and colors are hardcoded in the
  client (`Auto-routed` = primary, `Auto-resolved` = info
  with dashed border, `SLA compliance` = success). The
  server should not return legend metadata.
- The current showcase client **does not refetch this
  endpoint when the user changes the `impactRange`
  segmented control** — it uses the same hardcoded
  `COVERAGE_AUTO_ROUTED` / `COVERAGE_AUTO_RESOLVED` /
  `COVERAGE_SLA` arrays regardless of the active range.
  The contract is in place for the server to implement;
  the client will refetch when wired up.
